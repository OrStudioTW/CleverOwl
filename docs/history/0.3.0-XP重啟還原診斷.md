# 0.3.0：XP 重啟還原診斷

日期：2026-10-29（Asia/Taipei）。依據使用者提供的 `LSPosed_20261029_134114.zip`，以及「連原本那堂課 XP 都沒有保留」的補充。

## 結論與證據界線

0.3.0 在這份精確 APK 上已排除先前的 native 掃描失敗，功能註冊與本機 XP 修改有實機命中證據。但使用者測試確認課後增加的 XP 在重啟後完全未保留，包含原本課程應有的 XP。因此「實際、持久增加經驗」的需求驗收失敗；不能將其只描述成額外倍率未被採計。

這份日誌沒有課程提交內容、相應 HTTP 結果或伺服器核發 XP 回應，故尚無法判定是提交被拒絕、離線佇列未送出、伺服器未採計、讀取另一種 XP 統計，或其他同步問題。沒有從「本機 hook 命中」外推為「請求成功」或「伺服器已拒絕」。

預覽觀察只保留前 8 次資料，日誌中的初始 +20 發生在 XP 模型命中前；它不能代表之後所有課程按鈕的顯示值。程式中的「shared by path preview and session calculations」是實作說明，不是網路結算證據。

當次設定同時包含 MAX、timer=true、XP=3、加倍延長 1440 分鐘。四項改動並存，僅憑這份日誌無法將整堂課未保留歸因於其中單一功能。

## 程式核對

現有 hook 改寫的是本機 `XpBoostMultiplierInputs` 及既有道具的到期判定；沒有建立伺服器端加倍道具或訂閱，也沒有證明伺服器核發了修改後的 XP。

原始 APK 的 `CompletedSessionSurrogate` serializer 可見 `xpBoostMultiplier`、`hasBoost`、`xpPromised`、`expectedXpGain` 欄位。這說明本機完成模型與送出模型之間仍有待核對的邊界，並不證明該次請求的實際欄位值、是否有送出或伺服器如何處理。直接再放大本機總 XP、覆寫重啟後畫面，仍不能完成真正入帳的需求。

## 最小隔離驗證

1. 暫時關閉模組總開關，完整重開 Duolingo，在網路正常時完成一堂免費的一般課程。記錄同一種 XP 統計的課前／結算後／重新同步後數值，並確認課程進度是否保留。這能判斷原版流程是否正常提交。
2. 若原版正常，只啟用額外 ×3，會員維持原始、不延長加倍、不開無限時間，再用同類課程驗證。若只有這組整堂課不保留，才能將問題縮小到 XP 修改相關路徑。
3. 若原版也不保留，先處理帳戶／網路／離線佇列／統計來源；繼續改倍率無法解釋這種基準失敗。

若後續新增診斷，應只記錄提交前的數值欄位、送出／回應狀態及回傳核發 XP，不記錄認證、完整 body 或帳戶識別；也需區分來自網路與本機快取的資料。本次沒有依不足證據修改送出值，也沒有製作宣稱已解決入帳的新 APK。
